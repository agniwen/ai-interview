# 语音抢话与打断实测（2026-09-15）

文中 `src/`、`tests/` 和 `.env` 路径相对于 `apps/livekit-agent/`；`make` 命令在仓库根目录运行。

## 结论

当前 Qwen Realtime 可以被真实音轨打断，但有效插话的响应速度仍有明显波动。保留默认 `smart_turn`：它能忽略附和；直接切成 `server_vad` 虽然更快，却会把“嗯”误切成新一轮并生成无关回复。

本次没有修改生产轮次参数或加入第二套 STT/VAD。初次播报还受 LiveKit 的回声消除预热影响，不能将全部等待归因于上游判断；普通 interruption 参数也不直接控制 Qwen 的语义判断。新增了可重复运行的真实房间音频探针和录音证据，供继续调优。

## 方法

- 使用本项目 LiveKit 服务、Qwen 模型与适配器，两个 Python RTC 参与者通过实际音轨交流。候选人音频为 macOS Tingting 合成语音，24 kHz PCM16，约 20 ms 分包。
- 使用独立 `voice-probe-*` 房间，完成后删除，仅包含合成数据；未修改测试简历、未发招聘报告回调。
- 面试行为使用真实 `RealtimeInterviewAgent` 和两道合成题，验证语音信息保存与停顿。
- 为保证有足够长的语音可供打断，模式对比使用刻意要求长播报的独立 Agent；它的冗长话术不代表产品提示词效果。
- 记录 Qwen speech_started、Agent 状态与接收端 PCM。停声估算取 RMS > 150 的最后音频帧；包含网络和播放缓冲，不是纯模型推理耗时，也不是耳机声学测量。

## 有接收端录音的模式对比

| 场景                                                   | smart_turn                                           | server_vad（默认阈值、1000 ms 静音窗口）         |
| ------------------------------------------------------ | ---------------------------------------------------- | ------------------------------------------------ |
| “等一下，我补充一下，我负责的是订单服务，不是支付服务” | 约 4.51 s 停声；上游信号约 3.85 s                    | 约 2.67 s 停声；上游信号约 2.49 s                |
| “还有一点，我带六个人……”                               | 约 1.26 s 停声；上游信号约 1.07 s                    | 约 0.63 s 停声；上游信号约 0.46 s                |
| 短促“嗯”                                               | 原播报继续；该录音轮次被归入 ambient，未成为用户答案 | 约 0.78 s 停声；误识别为英文 and，并产生无关回复 |

每格为单次接收端录音观测，不是均值或 P95。前面的诊断轮次也出现了相同的速度/误打断取舍。语义模式另一轮曾把“嗯”写入转写但没有打断，因此不能承诺它总是被彻底过滤。

复核 LiveKit 1.7.1 的 `AgentActivity.push_audio` 后发现，默认首次播报有 3 秒 AEC 预热，在该窗口内实际输入会被替换成静音。首个插话在播报开始约 1 秒后注入，因此受到预热混杂影响，不能用于比较纯模型延迟。后续插话不受首次预热影响。

两种模式都未将首句的“等一下，我补充一下”保留在最终转写中，核心更正“订单服务，不是支付服务”保留。合成声音、音量和本地网络都会影响结果，需要真人复测。

Qwen 信号到 Agent listening 状态仅约 2–10 ms；接收端仍可出现约 0.17–0.66 s 的有声尾巴。上游信号之前的等待包含首次 AEC 静音窗口和模型判断，剩余尾巴包含音频发送与接收缓冲。

## 中性音色与预热后复测

切换 `longanlingxin` 并关闭情绪增强后，将首个插话延后至首次播报 4 秒以后，排除 3 秒 AEC 预热窗口。单次实测：有效插话到 Qwen 信号约 1.075 秒，到接收端停声约 1.24 秒；“等一下，我补充一下”完整保留。短促“嗯”未打断，也未进入用户答案。第二次有效补充能打断并保留团队人数及性能指标。该复测同时改变音色和注入时机，不能把差异解释为音色本身提高速度。

证据目录 `/tmp/ai-interview-voice-probe/neutral-warmed/`。探针现默认等待首次播报 4 秒后再注入插话；保留生产 AEC 预热配置，真实扬声器环境仍需人工测试。

## 真实面试 Agent 的语音行为

- 先说“我最近负责的项目，主要是”，停顿约 0.6 s 后继续完整经历：没有中途抢答，合并为一段转写。
- 职责、六人团队和 200 ms 性能结果已保存为 `in_progress`；后续追问架构决策，不重问开场。
- 另一轮连续补充后，已保存结果合并了订单服务、团队规模及 800 → 200 ms 的改善。
- 停顿轮次最后一段音频结束到面试官开始下一问约 4.4 s，说明回答后的等待也仍有优化空间，不应只关注打断速度。

## 调优取舍

1. 目前继续使用 `smart_turn`。当前面试更需要避免附和触发误答，普通 VAD 的副作用已经复现。
2. `silence_duration_ms` 只对 server_vad 有效，缩短它主要影响何时判定说完，不能解释为直接加速 smart_turn 插话。LiveKit Realtime 模式的多数 interruption 参数也不参与上游判断。
3. 若要求开口后数百毫秒稳定让出声音，需要单独验证客户端先降低播放音量、确认有效插话后再取消，或引入本地检测/支持更细打断配置的模型。前者会暂时压低附和期间的声音，后者会增加架构和延迟取舍；本次未把这些未经验证的方案塞入产品。
4. 后续真人验证应覆盖耳机/扬声器、背景人声、咳嗽、句中停顿和弱网；本次没有模拟物理麦克风与扬声器回声。

## 历史复现方式

本次验证使用 macOS Tingting 合成音频和独立 RTC 房间，分别测试打断、附和音和句中停顿。所用一次性探针依赖本机 `/tmp` 素材，已于 2026-09-17 按要求从仓库删除，不再提供指向已删除脚本的运行命令。正式协议与行为回归保留在 `apps/livekit-agent/tests/test_qwen_realtime*.py` 等测试中。

原始 `events.json` 和 `agent.wav` 保存在 `/tmp/ai-interview-voice-probe/<label>/`。`smart-interruption-stereo.wav` 是本次整理的 7.5 秒对比片段，左声道为合成候选人，右声道为接收端 AI 音频。临时目录不是长期档案。

脚本断言音频确实收到、受控长播报能被打断；停顿场景断言候选人说完前没有新播报，并且语音事实已保存。模式的延迟和误打断仍需人工阅读事件判断，不用一次采样设不稳定的毫秒阈值测试。
