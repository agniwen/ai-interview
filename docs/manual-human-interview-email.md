# 真人面试：HRD 手动发送候选人邮件

## 交互与边界

- 真人面试卡片「会议链接」左侧提供「邮件通知」。历史已取消卡片保留入口；已结束或已完成卡片不提供入口。
- 弹窗显示候选人、邮箱、面试名称、当前情况及时间，仅提供简短说明，不嵌入 HTML 正文预览。
- HRD 单选通知类型，再点击「确认发送」。打开、切换类型、关闭弹窗均不发送，也不修改面试状态。
- 仅新增候选人投递，不额外通知 HR 或面试官。现有内部飞书通知、Offer 邮件不变。
- 创建已安排时间的会议不再自动创建 `human_candidate_invitation_requested` 事件；该类型仅由人工确认邮件入口创建。未排期待办、候选人反馈、改期、取消和内部提醒仍保留，飞书日程同步调用不变。

| 通知         | 可发送条件                                                                     |
| ------------ | ------------------------------------------------------------------------------ |
| 面试邀请     | 会议尚未开始、链接有效、候选人等待接受或拒绝                                   |
| 面试安排确认 | 会议尚未开始、链接有效、候选人已接受                                           |
| 面试改期通知 | 存在与当前时间一致的改期事件，且保留原时间；会议未开始、链接有效、候选人未拒绝 |
| 面试取消通知 | 轮次或会议已取消；不附会议入口                                                 |
| 面试开始提醒 | 会议尚未开始、链接有效、候选人已接受；点击后立即提交，不是设置定时任务         |

改期后优先选中改期通知；其他情况按允许的类型选择默认项。没有可信原时间时不提供改期通知，不能凭空补造原时间。

邀请、安排确认和改期通知以实际会议状态为准：预约开始时间已到，但会议仍待开始、`startedAt` 为空且未到结束时间时，仍可发送。已到结束时间则阻断并提示先改期。只有「面试开始提醒」仍要求预约开始时间未到，避免发送过时的「即将开始」提醒。弹窗显示后端返回的具体阻断原因。

## 发送链路

同一场真人面试改期时保留候选人 Token、接受/拒绝状态及邀请版本，不延长旧 Token 的有效期。原链接未过期时，获取／复制仍复用原链接；原链接过期后，再获取／复制才生成新的有效期和 Token，旧链接失效。面试页面读取最新安排，入会仍受候选人响应、会议状态与入会时间限制。面试官 Token 规则未改。

1. GET `/api/w/:slug/studio/interviews/round-emails/human/:meetingId/:roundId/preview`：验证工作区、简历可见范围及真人面试修改权限，返回每类通知的短时签名确认信息（10 分钟）。
2. POST 同路径 `/confirm`：要求 `confirmed: true`、通知类型和签名；事务内再次校验状态、邮箱、会议时间、邀请版本与通知内容。
3. 在已有通知事件与投递表中原子创建记录。相同确认请求重复提交通过唯一键去重；重新打开弹窗并确认属于新的发送请求。
4. Worker 校验 `payloadSnapshot.manualHumanEmail` 与事件、操作者、收件人和正文匹配后发送。使用现有邮件 HTML 展示及五类候选人模板。
5. 活动记录展示操作者、通知类型、面试名称、收件邮箱、主题及真实发送状态。

接口返回 202 表示提交成功，不代表邮件服务商已投递。界面沿用产品确认的「邮件已发送成功」提示；实际结果以活动记录为准。

## 发布与测试

- 自动候选人邮件开关仍关闭。旧队列无本次人工确认快照的邮件仍被阻断，不能批量重新放行。
- Web/Server 和 Worker 需同步更新；旧 Worker 不认识新的人工确认快照，会继续拦截真人候选人邮件。
- 没有数据库迁移，仅扩展已有 JSON payload 的校验结构。
- 回归覆盖：打开/取消不发送、选择类型后显式确认、状态受限、权限、改期旧时间、Worker 放行与拦截、活动记录隔离。
- 真实投递验收需要运行 Worker，并由 HRD 在页面确认向测试邮箱发送；自动化测试不调用真实邮件或飞书服务。
