# Copy recruiting data into independent tables before switching runtime ownership

The recruiting-record split creates appropriately named destination tables for candidate, resume, recruiting data and the necessary dependent records, copies existing data, and switches runtime reads and writes only after validation in a controlled maintenance window. During the copy phase, the legacy `studio_interview` table and the source dependent tables retain their structure and data; copying must not delete source rows, rewrite their foreign keys, or create placeholder legacy recruiting rows for new records. The separately authorized post-cutover archive isolation below supersedes the foreign-key preservation requirement for links to live shared resources.

This deliberately incurs more migration work than repointing existing foreign keys: AI rounds, human rounds, offers, notifications, conversations and other dependent records reference the legacy recruiting table, so replacing only the parent would prevent creating new records without legacy writes. Destination names describe business responsibilities rather than migration versions, and the dependency inventory must cover Server, Worker, meeting processing, public links and recruiting-copilot consumers as well as the recruiting desk.

After cutover, legacy tables are not a live rollback replica: new business writes exist only in the destination model. Restoring an old application version therefore does not constitute a data-safe rollback. The accepted schema, execution evidence, backfill rules and recovery procedure are recorded in the [split plan](../plans/2026-09-05-recruiting-record-split.md). On 2026-09-05, the authorized development backfill committed 64,892 destination business rows and matching ledger entries. All source-table count/hash baselines remained unchanged, and a subsequent read-only replay verified all 64,892 existing target rows without inserting or updating any. This evidence validates copying and replay safety; full runtime cutover verification is tracked separately.

Replay never overwrites an existing target. Its ledger verifies the source mapping and the current target hash, rejecting changed sources, changed mappings, untracked target IDs or target edits made after cutover. Candidate and resume IDs are deterministic per legacy recruiting record; historical recruiting, round, conversation and invitation identities remain stable. Current successful evaluations and active/failed attempts are stored separately, preserving legacy artifacts rather than rerunning them.

The new search-index tables use `recruiting_record`; the Qdrant point and queued-job identity remains explicitly normalized to the historical `studio_interview` label so copying SQL records does not silently disconnect existing vectors. Shared parent deletion checks now inspect only the new recruiting tables. On 2026-09-05 the user explicitly requested removing legacy-table dependencies from jobs, users, workspaces, members, mailbox accounts and meetings. A separate migration removes the 72 foreign keys from the 33 legacy archive tables to live shared resources, including indirectly owned templates, versions and pool items. It preserves all archive rows, columns and archive-internal foreign keys, and all 144 destination foreign keys. Drizzle relations remove the matching cross-boundary navigation. This prevents live-parent CASCADE/SET NULL actions from altering the archives without requiring runtime reads of legacy data. Pool deletion continues to archive the shared pool item while retaining source references.
