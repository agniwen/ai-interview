# Use round-scoped evidence-backed interview reports

An **Interview Report** belongs to one AI interview round rather than to a candidate-level aggregate. A candidate may have multiple reports, and every report uses a shared, versioned contract that combines three source families: the frozen resume, submitted candidate forms, and candidate statements from that round. Each substantive conclusion must cite typed source evidence; generated conclusions are not evidence, source conflicts remain explicit, and missing required sources block submission.

## Decision

- `@app/shared` owns the strict Zod contract and inferred API types. `schemaVersion` identifies the contract shape; `reportVersion` identifies an immutable generation within one round. Raw JSONB is parsed at the DAO boundary and is never exposed to application consumers as `Record<string, unknown>`.
- A report may be regenerated while it is a draft. An HR member explicitly submits one version and selects one Feishu provider account linked to that member; the report persists that provider identity before any external call. Successful submission creates exactly one editable Feishu document for the round under that provider. The document contains the submitted version and the existing human-review sections. Other linked providers may not create or own another document for the same round.
- Report lifecycle and document creation lifecycle are separate. New reports move through `draft -> submitting -> submitted -> decided`; legacy migration additionally permits `migration_conflict -> submitted` after a human selects the one authoritative historical document. Document creation moves through `not_started -> creating -> configuring -> created`. The database claim that freezes the selected version and provider must commit before any Feishu request. Once Feishu returns a `documentId`, the system persists it in a separate short transaction before appending blocks, moving the document, or granting human access; access is granted last so people cannot edit during system configuration. A failure proven to occur before any document exists becomes `creation_failed` and may retry the same frozen version. An indeterminate create response, failure to persist a returned ID, or any failure after a document may exist becomes `creation_uncertain` and must never invoke the create API again automatically. The report becomes `submitted` only after the document ID is stored and required configuration succeeds.
- Entering `submitting` freezes both the selected report version and its AI interview round. The system rejects subsequent round field updates, status changes, resets, single deletes, and bulk deletes. After the Feishu document reaches `created`, the system never modifies its body. Human edits remain in Feishu and are not synchronized back into the report contract.
- Candidate hard deletion is rejected while any round-owned report is `submitting`, `submitted`, or `decided`, or while any legacy Feishu document remains linked. Draft-only reports may be deleted explicitly in the same transaction before deleting the candidate. Database foreign keys restrict bypass deletion; a future privacy-erasure or archival workflow requires a separate decision rather than silently orphaning an external document.
- Feishu is the editing and discussion surface, not the system decision channel. An authenticated HR member with visibility of the candidate makes the binary **Business Interview Entry Gate** decision in the system: advance to `human_interview`, or close as `rejected`. Only the submitted report for the candidate's terminal AI interview round is decision-eligible: that round is `completed`, has the greatest remaining `sortOrder`, and every remaining AI interview round is `completed`. This prevents an earlier round from ending the candidate pipeline while a later planned round is still pending or running. The report decision and candidate-stage transition are recorded atomically with audit history.
- Feishu document edit access does not grant system review authority. Ordinary HR members may review reports for candidates within their recruiting visibility scope, including reports they submitted themselves.
- Every immutable report version carries `contentKind`: `v1` for the strict evidence-backed contract and `legacy` for the typed legacy adapter. A round with exactly one linked historical document is migrated as an immutable `legacy` version in `submitted`; it may drive the Business Interview Entry Gate when the same terminal-round rules pass. A round with multiple historical documents enters `migration_conflict` and cannot drive a decision until a human resolves the document association with an audited mapping.

## Consequences

The existing automatic notification flow must stop creating a document as soon as a conversation report is ready. Report generation becomes a typed draft lifecycle, while document creation moves to the explicit submit action. Document identity and Feishu provider identity move from the current conversation-and-recipient notification row to a round-owned report record so retries and multiple linked Feishu accounts cannot create multiple documents for one round. Intermediate contract and generation milestones are not production-deployable until this automatic side effect is disabled or protected by a feature flag.

Historical conversation evaluations remain readable through a typed legacy adapter or backfill, but they do not silently acquire provenance that was never captured. A legacy evaluation may be regenerated as V1 only when its original evidence snapshot is verifiably bound to the same conversation, round, and context snapshot. Snapshots reconstructed from a later active context, current form submissions, or a guessed schedule entry are not sufficient; those evaluations remain typed legacy read-only records. Existing Feishu documents remain untouched.

All report submission, round mutation, candidate deletion, and final-decision paths use one database lock order: candidate first, then its rounds in stable order, then the round-owned report. Guards are re-evaluated inside that transaction after locks are acquired. No database transaction remains open while calling Feishu.

## Considered options (rejected)

- One candidate-level report aggregating multiple AI rounds: rejected because the product keeps one report and one Feishu document per round.
- Updating one Feishu document as new report versions arrive: rejected because automated edits could overwrite HR or executive review content.
- Requesting a new report version after Feishu submission: rejected for the first version because it conflicts with both one document per round and the no-system-edits rule.
- Making Feishu callbacks the decision channel: deferred; the first version keeps identity, visibility checks, audit, and stage transitions inside the authenticated system.
