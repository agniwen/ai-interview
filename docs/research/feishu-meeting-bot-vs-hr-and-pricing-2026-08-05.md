# 飞书真人面试：Bot 与 HR 创建会议及收费对比

查阅日期：2026-08-05

证据基线：飞书开放平台、飞书帮助中心和飞书官网当前公开资料。产品权益、价格和额度可能调整；正式上线前应以目标租户管理后台及飞书合同为准。

## 结论

对本项目，推荐采用混合方案：

1. **默认由发起 HR 的用户身份创建飞书日程和会议**。这样最接近员工手工使用飞书的习惯：日程进入 HR 主日历，HR 是组织者，可以邀请内部面试官、设置主持人、接收提醒并管理改期/取消。
2. **应用/Bot 负责后端编排、状态同步、事件消费、录制和逐字稿拉取，以及发送通知**。创建动作使用 HR 的 `user_access_token`，不代表其他后端工作也必须全部使用用户身份。
3. **HR 未完成授权或授权失效时，不静默切换创建方式**。界面应提示重新连接飞书；如业务允许，可显式提供“仅创建飞书会议链接”的 Bot 兜底选项，并明确该会议不会进入 HR 日历。
4. **不建议把“Bot 创建日历 + VC”作为默认方案**。虽然能生成日历事件，但组织者是 Bot，官方禁止 Bot 指定主持人，并要求 `allow_attendees_start=true`，与员工手工创建会议的行为存在明显差异。[创建日程](https://open.feishu.cn/document/server-docs/calendar-v4/calendar-event/create?lang=zh-CN)

收费方面：

- 会议录制没有官方单独公布的按次或按分钟价格，但受视频会议版本、会议用量和共享存储空间约束。
- 妙记语音转文字在基础版为每位成员每自然月 300 分钟；商业版、企业版不限制转写时长，但受企业存储空间限制。
- AI 智能纪要单独消耗 AI 额度。会议累计录制/AI 总结不超过 5 分钟不扣额度；超过 5 分钟后，每分钟消耗 0.5 点。

## 先区分三种创建方式

“用 Bot 创建会议”在飞书中存在两条不同链路，不能当成同一种方案。

| 方案                 | 调用身份                  | 主要 API                                        | 结果                                               |
| -------------------- | ------------------------- | ----------------------------------------------- | -------------------------------------------------- |
| A. Bot 直接预约 VC   | `tenant_access_token`     | `POST /vc/v1/reserves/apply`                    | 生成会议号、密码和链接；不生成日程，不显示在日历中 |
| B. Bot 创建日历 + VC | `tenant_access_token`     | Calendar v4 创建日程，并设置 `vchat.vc_type=vc` | 生成日历事件和会议，但组织者是 Bot                 |
| C. HR 创建日历 + VC  | HR 的 `user_access_token` | Calendar v4 创建日程，并设置 `vchat.vc_type=vc` | 日程和会议归属于 HR，最接近人工创建体验            |

飞书的直接预约接口明确说明：预约会议不会生成日程，也不会显示在日历中。它的 `end_time` 是会议号到期时间，不是完整的面试开始/结束时间模型。[预约会议](https://open.feishu.cn/document/server-docs/vc-v1/reserve/apply?lang=zh-CN)

### A. Bot 直接预约 VC

优点：

- 无需每位 HR 重新授权，服务可以稳定地后台批量创建。
- 可直接返回会议号、密码、浏览器链接和飞书客户端链接。
- 应用身份可以把内部 HR/面试官设置为 owner/主持人，而候选人只使用链接参会。
- 适合现有“创建面试记录 -> 复制链接”的最小替换。

问题：

- 不会生成飞书日程，没有参与人邀请、日历提醒、忙闲占用和 RSVP。
- `end_time` 只是预约到期时间，系统仍需维护自己的 `scheduledAt` 和真实面试结束时间。
- 直接预约接口没有 Calendar 创建日程所提供的日程幂等语义。远端成功、本地保存超时后盲目重试，可能创建重复会议。
- 官方旧版 VC 概述与当前具体接口页对 `tenant_access_token` 支持存在文档漂移；上线前必须以目标应用在 API 调试台的实际调用结果为准。

### B. Bot 创建日历 + VC

优点：

- 可以生成日历事件，添加内部参与人，并使用飞书提醒。
- 不依赖 HR 用户 token，后台自动化和批量处理相对稳定。
- 日程创建接口支持 `idempotency_key`，比直接 VC 预约更容易处理请求重试。

问题：

- 应用必须启用机器人能力，并对目标主日历或共享日历拥有 `writer` 或 `owner` 权限。
- 日程组织者是 Bot。官方错误码 `193101/193102` 明确规定：Bot 不能设置 `assign_hosts`，并且必须允许参与者发起会议。[创建日程](https://open.feishu.cn/document/server-docs/calendar-v4/calendar-event/create?lang=zh-CN)
- 员工会看到一个由应用组织的日程，不等同于 HR 本人发起。
- 提前排期会议的录制文件按官方规则归日程组织者。Bot 组织者下，妙记可见性、分享给 HR、AI 额度扣费对象都需要生产租户实测，不能仅凭字段推断。

### C. HR 用户身份创建日历 + VC

优点：

- HR 是真实日程组织者，日历、通知、忙闲、参与人和主持人行为与人工操作一致。
- 提前排期会议的录制文件归日程组织者，HR 可以直接收到并查看妙记。
- 审计清楚：可以回答“谁创建、谁改期、谁取消、录制归谁”。
- 智能纪要和用户可见文档本身也是用户权限模型，后续接入更自然。

问题：

- 当前用户必须完成 Calendar/VC 权限的增量授权。
- 后台长期排期需要 `offline_access`。refresh token 只能使用一次，刷新后旧 token 立即失效，因此必须串行化并原子保存新 token，避免并发刷新导致授权失效。[刷新 user_access_token](https://open.feishu.cn/document/authentication-management/access-token/refresh-user-access-token?lang=zh-CN)
- HR 撤销授权、离职、被移出应用可用范围或 refresh token 过期时，需要提示重新授权，不能静默失败。
- 如果 HR 同时在飞书客户端和本系统修改日程，需要明确单向或双向同步规则，避免互相覆盖。

### 妙记转写和存储

- 基础版：每位成员每月 300 分钟妙记语音转文字，会议录制、录音、上传文件和导入云文件共同消耗该额度。
- 商业版、企业版：妙记转写时长不限，但企业存储空间满后无法继续生成新的妙记。
- 通过会议录制生成妙记，单场最长支持 16 小时。
- 妙记与即时消息、邮箱和云文档共用企业存储空间。

### AI 智能纪要额度

当前官方规则：

- 单场会议开启 AI 总结或录制的累计时长不超过 5 分钟：不消耗额度。
- 超过 5 分钟：按累计时长每分钟消耗 0.5 点，不足 1 分钟向上取整。
- 同一场会议同时开启 AI 总结和录制时，时长去重后合并计算。
- 单场会议只扣一个成员的额度：优先扣会议组织者；组织者没有额度时，扣开启者；多次开启时扣最后一次开启者。
- 如果成员拥有智能纪要权限和额度，生成妙记时可能同时生成智能纪要并消耗 AI 额度。
- 旧的“飞书智能会议纪要企业版，每年 12,000 篇”产品已经停售，只对历史已购买企业继续有效，不能作为新项目报价基线。

来源：[智能纪要用量额度说明](https://www.feishu.cn/hc/zh-CN/articles/808156011479-%E6%99%BA%E8%83%BD%E7%BA%AA%E8%A6%81%E7%94%A8%E9%87%8F%E9%A2%9D%E5%BA%A6%E8%AF%B4%E6%98%8E)

## 面试用量估算

以下只估算 AI 智能纪要点数，不包含飞书主套件、存储扩容、实施服务或其他 AI 功能的消耗。

当会议时长超过 5 分钟时，可按下式粗略估算：

```text
单场点数 = 向上取整后的会议分钟数 × 0.5
年度点数 = 单场点数 × 月均面试场次 × 12
```

| 单场面试时长 | 每场 AI 额度 |
| -----------: | -----------: |
|      30 分钟 |        15 点 |
|      45 分钟 |      22.5 点 |
|      60 分钟 |        30 点 |
|      90 分钟 |        45 点 |

按每场 60 分钟估算：

| 月均面试量 | 月度 AI 额度 | 年度 AI 额度 |
| ---------: | -----------: | -----------: |
|     100 场 |     3,000 点 |    36,000 点 |
|     500 场 |    15,000 点 |   180,000 点 |
|   1,000 场 |    30,000 点 |   360,000 点 |

如果 180,000 点全部用于 60 分钟智能纪要，理论上约可覆盖 6,000 场/年，即 500 场/月。以 ¥9,900/年的公开套餐价格简单除算，约为 ¥1.65/场；这只是额度摊销示例，不是飞书给出的单场报价，因为同一额度还会被企业其他 AI 功能共享使用。

对于基础版妙记转写，每位录制归属者每月 300 分钟，理论上只能覆盖 5 场 60 分钟面试。若面试量较大，不能依靠把会议分散给不同 HR 来规避产品版本规划，应按企业实际合同和合规要求选择商业版或企业版。

## 创建身份对录制归属和扣费的影响

官方说明：提前安排的会议日程，录制文件归属者为日程组织者；临时发起的会议，录制文件归属者为会议发起者。[生成妙记](https://www.feishu.cn/hc/zh-CN/articles/386045971891-%E7%94%9F%E6%88%90%E5%A6%99%E8%AE%B0)

因此：

- HR 用户身份创建日程时，录制和妙记归属 HR，AI 额度也优先扣 HR/组织者，行为最可预测。
- Bot 创建日历时，组织者是 Bot。Bot 如何承接录制所有权、员工如何直接查看、AI 额度最终扣给谁，需要在目标租户做一次真实会议验证。
- Bot 直接预约 VC 时虽然可以设置内部 `owner_id`，但官方收费说明使用的是“会议组织者/开启者”口径。不能未经实测就把 `owner_id` 等同于最终扣费成员。

这也是推荐 HR 创建日程、应用负责后台处理的重要原因：身份、资源归属和费用归属更一致。

## 对当前代码的影响

当前仓库已经有应用身份基础设施，但 HR 用户身份链路尚未满足长期后台建会要求：

- 已有按应用获取和缓存 `tenant_access_token` 的服务，可复用于 Bot 直接预约和应用级 API。
- 当前飞书 OAuth scope 只有通讯录基础信息和邮箱，没有 Calendar、VC、智能纪要或 `offline_access`。
- 数据库账号表能够保存 access/refresh token，但当前代码没有 refresh token 轮换实现。
- 真人面试表目前只保存 LiveKit room 和 LiveKit 录制字段，没有创建身份、飞书 provider、Calendar event、VC reserve/meeting 或妙记 ID。
- 当前前端先创建面试轮次、再创建 LiveKit 会议。加入外部飞书调用后会出现本地半成功、远端重复创建等问题，需要由后端命令统一编排。

目标数据模型至少应记录：

- `meetingProvider`: `livekit | feishu`
- `feishuProviderId` / app ID
- `creationIdentity`: `app | user`
- `creatorUserId`、飞书 `open_id/user_id`
- `calendarId`、`calendarEventId`
- `reserveId`、实际 `meetingId`、`meetingNo`
- `joinUrl`、密码
- `minuteToken`、`noteId`、逐字稿/纪要文档 token
- `externalSyncStatus`、`artifactStatus`、`lastError`
- 创建、改期、取消的幂等键和飞书事件 `event_id`

## 推荐目标流程

```text
HR 点击“发起真人面试”
  -> 后端检查 HR 是否已授权 Calendar/VC/offline_access
     -> 已授权：用 HR user_access_token 创建日程 + VC
     -> 未授权：提示连接飞书
        -> 可选的显式兜底：Bot 仅创建 VC 链接，并提示“不进入飞书日历”
  -> 保存创建身份、Calendar/VC ID、链接和外部同步状态
  -> Bot 向 HR/面试官发送确认或失败通知
  -> 应用级事件接收端处理 meeting_ended / recording_ready
  -> 应用身份优先拉取录制和妙记逐字稿
  -> 如需 AI 智能纪要，再以具备权限的 HR 用户身份订阅和读取
```

责任划分：

| 能力                            | 推荐身份                           |
| ------------------------------- | ---------------------------------- |
| 创建日程和 VC                   | HR 用户身份                        |
| 给内部人员发机器人通知          | Bot 应用身份                       |
| 接收会议生命周期事件            | 应用事件接收端                     |
| 获取应用可访问的录制/妙记逐字稿 | 优先应用身份，失败时按资源权限处理 |
| 订阅/读取 HR 可见的智能纪要     | HR 用户身份                        |
| 改期/取消                       | 与原创建身份保持一致，不跨身份操作 |

## 上线前必须实测

1. 目标租户实际购买的是基础版、商业版还是企业版；妙记转写、存储和 AI 通用额度各剩余多少。
2. `tenant_access_token + owner_id` 在当前自建应用上能否成功预约 VC，并能否指定多个内部主持人。
3. HR 用户身份创建日程 + VC 后，内部参与人邀请、外部候选人网页入会、等候室和主持人行为是否符合预期。
4. Calendar API 创建的 VC 是否稳定产生项目需要的 `vc.meeting.*` 事件。
5. Bot 创建日历时，录制文件实际归属、HR 可见性及 AI 额度扣费对象。
6. Bot 直接预约 VC 时，录制文件和 AI 额度实际归属 `owner_id`、组织者还是录制开启者。
7. 录制结束后，应用身份能否在配置的数据范围内导出妙记逐字稿。
8. HR 撤权、refresh token 被并发使用、过期、离职和重新授权时的恢复流程。
9. 改期、取消及远端成功但本地超时后的幂等恢复。
