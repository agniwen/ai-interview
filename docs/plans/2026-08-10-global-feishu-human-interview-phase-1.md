# 全局飞书会议功能（第一期）实施计划

> 状态：已实现，待部署环境联调。
>
> 范围：仅实现全局开关与 LiveKit 流程隔离。飞书会议的后台补偿、监控与历史会议补建属于第二期，明确不纳入本文。

## 目标

将飞书会议作为真人面试的可选增强能力，而不是替代既有 LiveKit 面试。

```text
FEISHU_HUMAN_INTERVIEW_ENABLED=false（默认）
  ├─ 真人面试只创建并使用 LiveKit
  ├─ 候选人与面试官链接始终进入 LiveKit
  ├─ 不调用飞书预约、日程或参会人 API
  └─ 不处理飞书会议开始/结束事件

FEISHU_HUMAN_INTERVIEW_ENABLED=true
  ├─ LiveKit 链接仍始终可用
  ├─ 在本地真人面试创建后同步创建飞书会议和日程
  ├─ 改期与手动重试可同步飞书
  └─ 飞书会议事件可补充更新本地生命周期状态
```

## 已确认决策

1. 开关是部署级全局配置，不按组织、岗位或单场会议分别配置。
2. `FEISHU_BOT_ENABLED` 继续只控制飞书消息机器人；不得复用为真人面试飞书开关。
3. 未设置 `FEISHU_HUMAN_INTERVIEW_ENABLED` 时必须按 `false` 处理。
4. LiveKit 是候选人与面试官进入真人面试的固定入口；飞书会议链接只是开启功能后的补充入口。
5. 关闭开关后，既有飞书会议保留历史字段和链接，但不再产生新的飞书副作用。
6. 变更环境变量后需要重启长运行服务，确保飞书长连接按新配置注册或移除会议事件处理器。

## 非目标

- 不新增组织级或用户级开关。
- 不自动给历史纯 LiveKit 会议补建飞书会议。
- 不实现飞书同步失败的后台队列、告警或运营管理页。
- 不改变现有飞书消息接收、简历处理或 Bot 卡片能力。
- 不让飞书会议状态阻断 LiveKit token 签发或访问。

## 实施步骤

### 1. 集中定义开关与部署配置

- 在飞书 provider 配置模块新增 `isFeishuHumanInterviewEnabled()`。
- 逻辑仅在环境变量严格等于 `"true"` 时返回启用；其余情况返回关闭。
- 在 Web 集成运行与独立后端的 `.env.example` 中添加：

  ```env
  FEISHU_HUMAN_INTERVIEW_ENABLED=false
  ```

- 文档明确该变量不等于 `FEISHU_BOT_ENABLED`。

**验收：** 缺少飞书凭证且开关关闭时，真人面试仍可正常创建。

### 2. 将本地真人面试与飞书同步解耦

- `POST /human-interview-meetings` 始终先创建本地会议、轮次关联、面试官关联和 LiveKit 房间标识。
- 仅在开关开启时：解析飞书 provider、写入 `feishuProviderId`、获取 tenant token、创建飞书预约会议、创建日程并添加参会人。
- 关闭时直接返回本地会议，响应中的 `feishu` 为 `null`，不得请求飞书 API。
- 飞书开启时继续沿用已有的失败、冲突和未知状态语义；飞书失败不能删除本地会议。

**验收：** 关闭时可选择没有共同飞书应用来源的多个面试官，并且网络层没有飞书 API 请求。

### 3. 约束后续写路径

- `PATCH /human-interview-meetings/:meetingId` 始终先更新本地排期和候选人活动。
- 仅在开关开启且该会议已具备飞书同步信息时，才更新飞书预约和日程。
- `POST /human-interview-meetings/:meetingId/feishu-sync` 在开关关闭时返回明确的业务错误，不允许人工调用绕过开关。
- 保留现有飞书字段，不在关闭功能时清空，以保护历史审计和已有链接。

**验收：** 关闭后改期不会调用飞书；开启后原有飞书会议仍能保持同步与重试能力。

### 4. 隔离飞书会议事件订阅与处理

- 飞书 Bot 长连接仍由 `FEISHU_BOT_ENABLED` 控制。
- 仅在真人面试飞书开关开启时，为既有长连接注册 `vc.meeting.meeting_started_v1` 和 `vc.meeting.meeting_ended_v1` 处理器。
- 处理器入口再次检查开关，避免运行期间配置关闭但旧连接尚存时继续写库。
- 继续按 provider 与飞书会议 ID/会议号关联，并使用 provider event ID 保持幂等。

**验收：** 关闭时飞书事件不改变本地真人面试状态；开启时合法事件仍可更新状态。

### 5. 固化 LiveKit 访问契约

- 候选人与面试官邀请链接始终签发 LiveKit token，不依据飞书同步状态拒绝访问或重定向。
- LiveKit 的 `room_started` 与 `room_finished` webhook 继续负责基础生命周期。
- 飞书开始/结束事件仅作为开启集成后的另一可信事件来源，不影响链接的可用性。

**验收：** 无论开关状态和飞书同步状态如何，面试官复制的系统链接均可进入 LiveKit。

### 6. 调整前端默认体验

- 安排真人复面弹窗默认只承诺“创建线上真人复面”，不默认承诺飞书会议和日程。
- 关闭时不依据飞书应用来源禁用面试官选择。
- 仅当会议返回飞书数据时，展示飞书会议链接、同步状态与重试入口。
- LiveKit 候选人/面试官链接保持“当前使用”的主入口标识。

**验收：** 关闭开关后的 UI 不暴露飞书选择限制或飞书失败提示；开启后已有的飞书信息可正常展示。

## 测试计划

### 后端

1. 配置默认关闭，显式 `true` 才开启。
2. 关闭时创建会议：返回 200、`feishu: null`、零飞书 HTTP 调用。
3. 关闭时创建会议：允许不同飞书 provider 或未绑定飞书的面试官。
4. 关闭时改期：本地时间更新成功、零飞书 HTTP 调用。
5. 关闭时重试飞书同步：返回明确拒绝，零飞书 HTTP 调用。
6. 关闭时飞书生命周期回调：不查询或更新本地会议。
7. 开启时保留创建、改期、失败重试、冲突、未知结果和事件幂等的既有覆盖。
8. 开启、关闭两种状态下均验证 LiveKit token 可签发。

### 前端

1. 面试官选择不因飞书 provider 不同而被禁用。
2. 仅当响应中存在 `feishu` 时展示飞书会议链接与重试入口。
3. 候选人和面试官 LiveKit 链接始终展示并可复制。
