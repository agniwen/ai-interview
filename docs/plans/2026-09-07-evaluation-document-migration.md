## 发布顺序（需要单独部署授权）

1. 在维护窗口暂停旧 Web/Server 和 Worker 的写入及相关定时任务。
2. 备份数据库，按项目既有 Drizzle 流程应用 `20260907160000_record_evaluation_document`。这是新增表、历史文档关联回填和缺失真人提交 outbox 回填；不转换通知类型。
3. 发布新版 Web/Server 和 Worker。不要让旧生产者与新生产者混跑。确认新表和读路径可用。
4. 从 `apps/server` 运行只读检查：

   ```sh
   bun --env-file=../web/.env src/scripts/migrate-evaluation-documents.ts
   ```

5. 确认目标环境和基线后，执行同一脚本加 `--apply`。脚本在事务内锁住通知写入，检查冲突、备份原行、改类型，并验证除了 type 以外所有字段未变。不创建通知事件、不更改投递状态。
6. 恢复新版定时任务。4 条 waiting_document 会按原定重试时间被处理；没有文档时先建表再回填。没有对应飞书绑定或配置时保留失败信息，修复绑定后重试。
7. 抽查 AI 正常结束、无 AI 的真人正式提交、后续真人轮次和结论修正；确认同一招聘记录使用同一文档，系统报告仍各自独立。

## 恢复与历史内容

- 原通知行保存在 `recruiting_maintenance.evaluation_document_notification_backup`。回退 type 前必须停写，逐行确认当前记录除 type 外仍等于备份；有后续变化的记录不能直接覆盖。不要删除新文档或文档关联。
- 已有真人评价的文档优先成为主表。没有真人评价时选最新历史通知文档。旧文档不会自动合并或删除，仍可从历史通知访问，避免覆盖飞书里的人工编辑。
- 若多个真人评价已经写入不同文档，类型迁移会报错，必须人工核对内容；不得只改 block_id 或 URL。
- `creating` 且 document_id 非空：重试继续同一份文档的初始化。不要清空 ID。
- `creating` 且 document_id 为空：创建结果未知，不自动重建。管理员应核对飞书实际结果；找到文档后恢复准确关联，或证明文档不存在后再撤销该创建意图。不要盲目重发创建请求。

## 隔离验证

### Platform 调试入口的迁移补齐

- 报告通知列表同时包含历史手动投递与 Worker 的 `ai_report_ready`；支持完整投递状态，消息 ID 兼容 `provider_message_id` 与旧字段。
- 早期 Worker 投递缺少会话 ID 时，只回溯其原始事件的会话，不猜测候选人最新轮次、不改历史身份字段。没有任何准确会话关联的历史通知仍不能 AI 预览或重发。
- 无文档 URL 的旧通知可读取招聘记录的主评价表；有旧 URL 的记录继续访问原文档，不覆盖历史关联。打开文档先通过实际文档所属应用为当前管理员授权。
- 手动重发调用自动发送使用的同一富卡片/评价表入口。Worker 原始行保持不变，重发使用独立的非事件投递行；已有历史手动行可以继续重发，并校验成员资格和最新飞书绑定。
- 正在发送或等待 Worker 重试的记录拒绝手动重发；同一接收人的并发点击被串行领取。手动发送抛错时保守记录为 `unknown`，不自动重试；管理员应先核对飞书，再决定是否手动重发。进程在 `sending` 时退出也需要人工核对，不可直接批量重置。
- 部分唯一索引的生产者冲突判断同步更新，旧自动重试不能覆盖手动发送中的状态。其他面试事件仍由其既有通知运维入口管理，不混入这个 AI 报告调试列表。
