# Offer 确认发布、邮件分享与候选人回复方案

日期：2026-09-11。状态：核心产品流程已由用户确认，本文整理实施边界；尚未实施。

## 1. 已确认的目标

- HR 编辑 Offer 后，通过「确认并发布 Offer」定稿，之后可以发送邮件或手动复制链接。
- 候选人通过专属链接查看 Offer，提交接受或拒绝。
- 候选人提交接受或拒绝后有对应的机器人提醒；打开或查看 Offer 不提醒。
- HR 可以在内部页面代候选人记录接受或拒绝，处理线下回复及候选人页面异常。
- 候选人拒绝只记录「已拒绝」，不自动结束招聘，由 HR 决定继续沟通或结束。
- Offer 内容状态、邮件发送状态、招聘流程状态分别记录。
- Offer 流程中的每个有效业务动作都写入候选人活动记录，形成可追溯的完整时间线。
- HR 确认只有一次明确的发布动作，本期不增加审批层级。

## 2. HR 操作流程

### 2.1 编辑与发布

1. 在「发 Offer」节点填写职位、Base 月薪、奖金、期权、预计入职日、有效期和对外说明。
2. 保存为「草稿」，支持编辑、预览和删除；草稿不能对外分享或接受回复。
3. 点击「确认并发布 Offer」，检查对外条款与有效期，确认后记录发布人、发布时间和不可变的本次发布快照。
4. 状态变为「待候选人回复」，显示「发送邮件」「复制 Offer 链接」「撤回 Offer」。已发布内容不可直接覆盖修改。

「确认并发布」表示 HR 已定稿并允许对外访问，界面不使用含义模糊的「生效」。发布本身不自动发送邮件。

### 2.2 发送邮件弹窗

| 字段       | 行为                                                                 |
| ---------- | -------------------------------------------------------------------- |
| 收件邮箱   | 默认候选人邮箱，必填并校验格式；更改本次收件地址不静默改写候选人档案 |
| 发件邮箱   | 使用已配置的系统发件地址，只读展示                                   |
| 邮件主题   | 提供包含公司、职位的默认主题，HR 可编辑                              |
| 邮件正文   | 提供默认文案，HR 可编辑并预览                                        |
| Offer 链接 | 系统固定插入「查看并确认 Offer」入口，不允许通过编辑正文误删或替换   |

- 提交按钮为「发送邮件」，发送前展示完整收件地址与内容。
- 只有 HR 在弹窗主动提交才创建本次邮件发送任务；发布、保存、推进节点均不隐式发送。
- 记录提交人、收件邮箱、主题、最终正文、对应发布快照、供应商消息编号、时间和发送结果。
- 邮件供应商确认接收请求后标记「邮件已发送」；不将其解释成已送达、已读或已接受。
- 失败可重试；超时且结果不明显示「发送结果待确认」，先核对供应商结果，避免盲目重发。
- 按一次提交建立幂等身份；重复点击及自动重试沿用该身份。HR 明确再次发送是新的发送任务，并保留此前记录。

### 2.3 手动复制链接

- 仅对当前有效发布开放复制，使用与邮件相同的候选人入口，不创建另一套 Offer。
- 复制可记录操作人和时间，但不标记邮件已发送，也不推断候选人已收到。
- 即使从未通过系统发送邮件，候选人也可以通过手动分享的有效链接回复。

### 2.4 HR 代录候选人回复

- 「待候选人回复」状态同时提供「记录接受」「记录拒绝」，作为电话、微信、线下回复和候选人页面异常的兜底入口。
- HR 提交前二次确认，并明确提示这是代候选人录入结果。拒绝原因可选，另有内部备注用于说明回复渠道或异常情况。
- 保存回复结果、回复时间、实际操作 HR、回复来源和内部备注；回复来源显示为「候选人在线确认」或「HR 代录」。
- HR 代录遵守与候选人在线回复相同的有效发布、有效期和并发规则，但不触发“候选人已操作”的机器人提醒，避免给操作人发送误导通知。
- 已有最终回复时不能直接覆盖。录错结果需要有权限的 HR 通过单独的纠错操作处理并留下审计记录，不能通过再次点击相反按钮改写历史。

## 3. 候选人页面

1. 公开地址使用 `/offer/{token}` 形式，Token 即访问凭证，本期不增加邮箱验证码、登录或其他身份验证。
2. 打开有效链接后直接展示本次已发布的对外条款：公司、候选人、职位、薪酬组成、预计入职日、Offer 有效期和对外说明。
3. 打开或刷新页面不发送机器人提醒，也不触发接受或拒绝；每次成功访问均记录「Offer 链接被访问」活动，访问者标记为「未验证访问者」。
4. 页面提供「接受 Offer」「拒绝 Offer」，明确二次确认；拒绝原因可选，接受后的备注不作为本期必需字段。
5. 提交后显示结果及时间，按钮变为不可重复提交。再次访问能查看自己的既有结果。

对外页面不返回内部备注、谈薪过程、候选人期望、流水材料或其他招聘记录。现有 notes 字段不能整体直接公开，需要明确拆分对外说明和内部备注；历史备注默认按内部内容处理。

专属链接使用足够随机、不可枚举的 Token，服务端只保存摘要，并绑定工作区、招聘记录和发布快照。任何取得链接的人都可以查看并提交回复，因此页面和邮件需提示 HR 将链接作为敏感信息定向发送，不在公开群聊传播。发布有效期必须明确；按页面展示的时区和截止时刻执行校验。撤回、过期、重新发布、招聘结束或回退导致发布失效时，旧 Token 立即失效；邮件预览器、页面刷新和 GET 请求不产生回复，但成功访问仍按真实来源写入访问活动。

## 4. 状态与 HR 后续处理

### 4.1 Offer 与邮件状态

| Offer 状态   | 主要动作和限制                                                 |
| ------------ | -------------------------------------------------------------- |
| 草稿         | 编辑、预览、删除、确认并发布                                   |
| 待候选人回复 | 发送邮件、复制链接、记录接受、记录拒绝、撤回；禁止直接修改条款 |
| 已接受       | 查看条款与回复记录；由 HR 推进背调，不自动进入背调或入职       |
| 已拒绝       | 查看原因、继续沟通、结束招聘；不自动结束招聘                   |
| 已过期       | 不再接受回复，可基于旧内容重新编辑并发布                       |
| 已撤回       | 旧链接失效，可基于旧内容重新编辑并发布                         |

邮件状态按发送任务独立记录：未发送、待发送、发送中、已发送、失败、结果待确认、已取消。主卡展示最近一次任务结果与历史入口，新的发送失败不能抹去此前成功发送的事实。

示例：「待候选人回复 · 邮件未发送」「已接受 · 邮件未发送」均合法，后者可能通过手动分享链接完成。

### 4.2 候选人拒绝

- Offer 记录「已拒绝」、拒绝原因、回复时间和来源；来源明确区分候选人在线确认与 HR 代录。招聘主记录仍在 Offer 阶段，不写成已结束，不自动给招聘节点下失败结论。
- 「继续沟通」记录 HR 跟进动作，保留原拒绝结果。需要再次邀约时，基于原条款生成可编辑草稿，再由 HR 确认发布；即使条款不变，也产生新的发布快照与链接。
- 「结束招聘」使用现有 HR 结束流程，记录结束原因和操作人。
- 已接受、已拒绝的历史发布和回复不可覆盖；不能通过简单修改 status 抹掉原回复。

### 4.3 并发规则

- 对同一发布的首次有效回复以事务内校验并落库的结果为准；相同回复重试返回既有结果。仅候选人在线提交生成机器人通知，HR 代录不生成该通知。
- 已接受后再提交拒绝，或已拒绝后再提交接受，返回既有结果与说明，不相互覆盖。
- 回复与 HR 撤回、重新发布、阶段回退并发时，锁定同一招聘记录并核对当前有效发布；失效发布不得改变招聘进度。

### 4.4 Offer 活动记录

复用现有候选人「活动记录」及 `recordCandidateActivity` / `recruitingEvent` 链路，不新增活动表、活动时间线或另一套审计模型。Offer 新流程只补齐对应事件和展示文案；已有招聘节点事件与通知发送记录继续按现有方式出现在活动记录中。

| 动作           | 事件 action                       | 活动文案及必要详情                                |
| -------------- | --------------------------------- | ------------------------------------------------- |
| 创建草稿       | `offer_draft_created`（已有）     | 创建 Offer 草稿；关联 Offer ID                    |
| 保存编辑       | `offer_draft_updated`（已有）     | 更新 Offer 草稿；记录变更字段名                   |
| 预览 Offer     | `offer_previewed`                 | 预览 Offer；关联当前草稿或发布快照                |
| 删除草稿       | `offer_draft_deleted`（已有）     | 删除 Offer 草稿                                   |
| 确认并发布     | `offer_published`                 | 确认并发布 Offer；记录发布人、发布快照和有效期    |
| 提交发送邮件   | `offer_email_send_requested`      | 提交 Offer 邮件；记录脱敏收件邮箱和发送任务 ID    |
| 再次发送邮件   | `offer_email_resent`              | 再次发送 Offer 邮件；关联新的发送任务 ID          |
| 复制链接       | `offer_link_copied`               | 复制 Offer 链接；不记录原始 Token                 |
| 撤回 Offer     | `offer_withdrawn`                 | 撤回 Offer；记录原因和失效发布                    |
| 候选人在线接受 | `offer_candidate_accepted`        | 候选人通过公开页面接受 Offer；来源为在线确认      |
| 候选人在线拒绝 | `offer_candidate_declined`        | 候选人通过公开页面拒绝 Offer；记录拒绝原因        |
| HR 代录接受    | `offer_acceptance_recorded_by_hr` | HR 代录候选人接受；记录操作人、来源和内部备注     |
| HR 代录拒绝    | `offer_decline_recorded_by_hr`    | HR 代录候选人拒绝；记录操作人、拒绝原因和内部备注 |
| 纠正回复       | `offer_response_corrected`        | 纠正 Offer 回复；保留原结果，记录纠正前后值及原因 |
| 继续沟通       | `offer_follow_up_started`         | 对已拒绝 Offer 继续沟通；记录操作人和备注         |
| Offer 过期     | `offer_expired`                   | Offer 到期失效；记录发布快照和到期时间            |
| Token 失效     | `offer_token_invalidated`         | Token 因撤回、重新发布、招聘结束或阶段回退失效    |

- 「结束招聘」和「推进背调」复用现有招聘流程事件，不重复新增 Offer 事件；事件详情关联当前 Offer 和发布快照即可。
- 邮件及机器人发送中、成功、失败、重试等结果复用现有通知发送记录在活动时间线中的展示，不再重复写一套 Offer 投递事件。
- 候选人打开或刷新 Token 页面记录 `offer_link_accessed`，动作主体显示为「未验证访问者」，不显示为候选人已查看，也不触发机器人提醒。
- 每个成功动作只写一条对应事件；接口重试命中同一业务结果时不重复写事件，HR 明确再次发送邮件除外。
- 事件详情保留 Offer ID、发布快照 ID、来源和必要结果，不保存原始 Token、完整邮件正文或未脱敏邮箱。
- 填写字段、打开或关闭弹窗等没有提交业务结果的前端操作不写活动事件。

## 5. 机器人提醒

复用现有内部飞书机器人及通知发送记录、重试机制。新增 Offer 事件，不能仅复用面试事件名称。

| 候选人事件 | 提醒文案要点                                                     | 卡片入口         |
| ---------- | ---------------------------------------------------------------- | ---------------- |
| 接受 Offer | 候选人已接受，可由 HR 确认后续背调安排                           | 查看候选人 Offer |
| 拒绝 Offer | 候选人已拒绝，展示原因或「未填写原因」；请决定继续沟通或结束招聘 | 前往处理         |

打开、刷新或仅查看 Offer 不生成机器人提醒。只有候选人通过公开页面成功提交接受或拒绝后，才创建对应业务事件；HR 代录只写审计记录和页面状态，不伪装成候选人操作。

通知接收人默认固定为本次 Offer 的发布 HR，发布时记录其用户身份，不根据之后打开页面或重发邮件的人改变接收人。本期不新建负责人角色或自动群发给所有 HR。

机器人卡片包含候选人姓名、职位、动作、操作时间、拒绝原因和内部详情链接；默认不包含薪资。链接进入需要登录且校验工作区权限的 HR 页面，不能携带候选人公开令牌；卡片本期只导航，不直接执行进入背调或结束招聘。

- 发布 HR 有飞书账号时发送机器人提醒；未绑定时沿用现有内部邮箱兜底，并在页面明确实际渠道。
- 若发布 HR 已离开工作区或无有效接收地址，显示通知异常，允许有权限的 HR 指定有效接收人后重试，不静默丢失或扩大通知范围。
- 候选人回复与通知事件在同一事务内保存，Worker 在提交后异步投递。发送失败不撤销候选人回复，页面始终显示真实业务结果。
- 沿用现有 1、5、15 分钟重试策略及结果不明/人工处理状态；按发布、业务事件、接收人和渠道去重。
- 区分候选人本人回复与 HR 代录历史/线下回复。HR 代录不生成候选人操作机器人提醒。

## 6. 实施结构与现有行为调整

### 6.1 数据与后端

- 继续以 recruiting_record、recruiting_offer 及 recruiting_node_state 为当前业务归属，不写回已归档的 studio 表。
- 保持一条招聘只有一份当前 Offer 的产品体验；增加内部发布快照和回复历史，支持撤回重发后追溯，不恢复多个并行有效 Offer。
- 现有 recruiting_offer.version 固定为 1 的约定不直接当成新快照序号使用；为发布快照设计独立标识及序号。页面仅管理当前版本，历史只读。
- Offer 所属能力负责保存、发布、撤回、邮件提交、HR 代录回复和后续处理；公开接口根据 Token 读取对外投影并接收候选人回复。二者共用应用动作与事务约束，保持工作区隔离。
- 新增发布人/时间、Token 摘要/有效期、条款快照、回复来源/时间、代录操作人和发布关联。邮件、机器人通知使用独立的发送任务与记录；不保存首次查看状态。
- 复用现有 `recruitingEvent` 和候选人活动时间线，按 4.4 增加 Offer 事件及展示文案，不新增活动存储或时间线组件；异步投递结果继续读取现有通知发送记录。
- 候选人拒绝不再复用当前 respondOfferDraft 将拒绝映射为节点 fail 并关闭招聘的逻辑；保留 HR 主动结束流程。
- 过期校验在服务端每次公开读取和提交时执行，不能只依赖页面倒计时或后台定时任务。
- HR 邮件主动发送与内部机器人通知分别接入现有供应商适配和可靠发送能力；新增 Offer 类型、模板、发布关联及失效处理。

### 6.2 界面

- HR Offer 卡片：当前业务状态、邮件结果、条款预览、按状态显示的动作及历史记录。
- 新增发布确认、发送邮件、复制链接、撤回、HR 代录回复和拒绝后跟进交互，复用现有弹窗、表单与状态提示组件。
- 现有候选人活动时间线增加 Offer 事件文案，沿用当前的动作主体、结果和时间展示。
- 新增候选人公开 Offer 页面，优先支持手机浏览、键盘操作、明确错误提示及提交后的焦点管理。
- 机器人卡片导航到候选人详情 Offer 标签；HR 刷新或回到页面时可看到最新回复，不依赖机器人发送是否成功。

### 6.3 历史兼容与发送边界

- 历史 sent/sentAt 仅证明曾被人工标记发出，不补造邮件成功记录。保留原时间，显示「历史人工标记发出」及「无系统邮件发送记录」。
- 历史 accepted/declined 保留原结论与历史语义，不伪造为候选人在线确认；已经结束的招聘不因迁移自动重新打开。
- 迁移不自动生成并分发公开链接、不发送历史 Offer、不重放历史接受/拒绝通知。旧记录需要公开分享时，由 HR 显式确认本次对外内容和邮箱。
- 现有候选人面试邮件暂停策略继续有效。本方案只启用用户明确要求的 Offer 主动发送，不借此恢复邀请、改期或面试提醒邮件。
- 开发和验证阶段使用测试供应商或指定测试地址；不向真实候选人发送调试邮件或机器人测试消息。

## 7. 验收清单

1. 草稿可编辑；确认发布后条款锁定，记录发布人，生成当前有效链接。
2. 邮件弹窗默认值正确，正文可编辑且固定入口完整；取消不发送；成功、失败、超时结果各有准确展示。
3. 邮件和复制链接使用同一发布；仅复制不改变邮件状态；未发系统邮件也能完成候选人回复。
4. 对外页面不泄漏内部字段；Token 摘要、工作区、当前发布及有效期均在服务端校验，无额外身份验证。
5. 打开和刷新不提醒；候选人在线接受与拒绝分别生成正确的机器人提醒，重复提交不重复通知。
6. HR 可以代录接受或拒绝，页面明确显示来源、操作人和备注；代录不生成候选人操作提醒。
7. 接受后由 HR 推进背调；拒绝后招聘仍在 Offer 阶段，HR 可继续沟通或明确结束。
8. 拒绝后重新发布保留原回复与条款历史，旧 Token 无法操作新版；已接受内容不可直接修改。
9. 并发接受/拒绝、HR 代录/在线回复、撤回/回复、回退/回复及邮件重试均不覆盖有效结果、不重复发送。
10. 邮件或机器人故障不影响已保存的业务事实；通知异常可见、可追踪、可恢复。
11. 历史人工发送不显示为邮件成功；历史已结束记录不被重开，其他面试邮件保持暂停。
12. 创建、编辑、预览、删除、发布、邮件提交与结果、复制、撤回、访问、在线回复、HR 代录、纠错、继续沟通、结束、推进、过期、Token 失效和机器人投递均产生对应活动记录。
13. 状态动作和活动记录保持原子一致；幂等重试不产生重复活动，时间线能按 Offer 和发布快照还原完整过程。

实施顺序：发布快照与状态迁移 → HR 发布/分享界面 → 候选人公开页面与回复 → 邮件与机器人投递 → 历史兼容和端到端验收。每步按行为风险完成定向测试，最后检查 Server/Worker/Web 类型及目标浏览器表现。
