## 外键约束与身份建议

旧 AI 轮次、真人轮次、Offer、评估、人才池导入、上传批次项、会话、通知、表单、模板绑定、快照及日志等表存在指向旧主表的真实外键。会议招聘上下文还存在工作区复合外键。

仅创建新主表并替换查询，无法向旧附属表写入只存在于新主表的新招聘记录。已决定复制必要附属表；不得修改原表外键或往旧主表补占位记录规避约束。完整决策见 [ADR-0036](../adr/0036-copy-recruiting-data-into-independent-tables.md)。

迁移已保留招聘记录、面试轮次、邀请、会话及外部会议的原 ID 和 token。新增人才与简历使用各自身份，不把旧招聘 ID 同时解释成三种身份。保留 ID 不能替代外键处理。

复制数据不应触发邀请、邮件、会议创建或评估重跑。新运行时写入开始后，重跑回填不得覆盖新数据。切换后不能仅回退应用版本就宣称数据已回滚，因为旧表不含新产生的业务数据。

人才池导入与上传处理的关联同样新建目标表，例如 `recruiting_pool_import`、`recruiting_upload_batch_item`。有状态父表、间接外键和多态 ID 的保护范围通过完整依赖清单确定，不能一部分复制、一部分仍回写旧业务记录。岗位、成员、模板定义、通用对象存储等独立资源不因被引用就整体复制；此类资源不属于本次冻结的旧招聘附属数据，迁移不得修改其原行。

主表只保存具体当前节点；大阶段由共享映射计算。节点表唯一键为 `(recruiting_record_id, node)`，阶段状态与结果需按节点校验。主表和节点表、业务记录、事件由一个事务维护；业务详情中的旧结果不是当前流程自动采用结果的依据。

索引围绕工作区、可见范围、当前节点、节点处理结果与排序字段建立；跨表引用检查同一工作区和同一招聘记录。列表按后端条件筛选、去重、分页，数量查询复用同一条件，不读取全量数据后在浏览器筛选。

## 已授权执行方案

1. 清点源主表、附属表、间接引用、JSON 引用、公开链接与后台队列。产出源到目标的字段映射，不改源表。
2. 新建目标 schema、约束、关系和迁移工具。新建表的迁移 SQL 不允许包含针对源表的 ALTER、UPDATE、DELETE、DROP 或重建约束操作；核对生成 SQL 而非直接执行自动差异。
3. 实现只读预检、可重入复制回填、来源映射及完整性报告。映射保存到新迁移台账，人才/简历的新 ID 在重跑时稳定；旧招聘、轮次和公开链接相关 ID 保持稳定。重复执行只核验一致性；存在源/映射变化、未受管目标或目标被修改时停止，不自动更新任何已迁移行。
4. 替换所有业务读写所有者及消费者，而非仅改招聘台 DAO。统一创建、面试安排、评价决定、节点推进、结束和恢复的事务；保留原可见范围、工作区权限、解析幂等与评估版本守卫。
5. 完成新节点筛选及详情动作，快捷入口将前置节点标记 skipped。回退先将旧有效结果记入历史，再使目标之后的节点失效；目标的指定状态必须合法，引用旧面试结论也必须由明确动作确认。
6. 在隔离测试数据库验证迁移与实际业务链路；不把项目环境变量指向的数据库默认视为测试库。实际业务数据库执行需在交付时明确目标实例、维护窗口及备份位置。
7. 维护时等待活跃面试完成、停止相关写入和消费者、保存队列及源数据基线、做最终回填和核对、切换所有消费者后恢复。保留未发送通知与待处理任务身份；已发通知不重放，邀请 token 和外部资源 ID 不重建。

历史含糊节点已按用户授权结合上下文推断，并在迁移报告保留依据；轮次数量、CEO 标签或已到后续节点只能帮助选择节点类型，不能作为通过结论。缺失真实结果保留未知或跳过，不丢弃原始记录。

切换前验收失败可以保留旧代码继续服务；切换后产生新写入则先保护目标数据，优先修复新体系。不能通过直接切回旧应用丢掉新产生的数据。迁移源不作为双写副本，不添加旧主表占位行。

- 源表结构与数据的保护按确认边界验证；目标数据逐表计数、关键字段和关联完整性核对。
- 单份／批量上传、人才池普通导入与重新导入、直接创建 AI 和已有记录发起 AI 均验证。
- 真人排期、取消重排、评价、旧邀请链接、报告与会议关联仍有效。
- Server、Web、Worker、会议处理和智能体使用同一目标数据体系。
- 筛选、阶段数量、结束、恢复以及并发操作按同一业务规则处理。
- 不生成虚假的历史通过结论或节点时间，不重复发送历史通知。
